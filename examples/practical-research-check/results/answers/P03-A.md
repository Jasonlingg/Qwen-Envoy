**Measure a matched latency baseline first; defer optimization until it identifies the bottleneck.** No deployment measurements exist, and 4,000 input versus 200 output tokens does not establish whether prefill or decoding dominates.

**What to measure.** Pin the GPU, serving-engine version, model/Envoy v5 adapter, inference quantization, tokenizer/template, thinking mode and sampling settings. Count actual generated tokens, including reasoning; Qwen3-8B enables thinking by default. Its QLoRA training history alone does not specify inference precision. [Qwen3-8B model card](https://huggingface.co/Qwen/Qwen3-8B)

For each request, collect client submission, server arrival, first scheduling, first token and completion timestamps:

- **Queueing:** server arrival to scheduling, plus any application-side wait. Two simultaneous requests can contend for scheduling or memory even without other traffic.
- **Prefill:** processing the prompt and constructing KV state. Record scheduled-to-first-token time, recognizing that this includes scheduling interference and first-token generation—not just GPU kernel time.
- **Decoding:** first-to-last-token duration and inter-token gaps. For exactly 200 generated tokens, mean time per subsequent token is that duration divided by 199.
- **End-to-end:** client submission to complete, parsed extraction. Also record TTFT and the time until **both** readers finish; streaming the first token may provide little practical value here.

These distinctions follow the lifecycle documented in [vLLM v0.8.5 metrics](https://docs.vllm.ai/en/v0.8.5/design/v1/metrics.html); use equivalent instrumentation if another runtime is selected.

**Cold starts need separate measurements:** activation-to-ready, weight/adapter loading, compilation/warm-up, and first-request latency. Distinguish a new process with weights already on disk from a download-inclusive start. A warm process with an empty prefix cache is another distinct condition.

**Evidence and limits.** KV-cache memory savings, prefix reuse and kernel speed are different mechanisms. vLLM v0.8.5 documents approximately doubled KV capacity with FP8, but **no latency improvement in that implementation**. [Quantized KV documentation](https://docs.vllm.ai/en/v0.8.5/features/quantization/quantized_kvcache.html) FlashAttention-2 reports roughly 2× attention speedup over FlashAttention on A100; that is not a measured Qwen3-8B extraction-service speedup. [FlashAttention-2 v1](https://arxiv.org/abs/2307.08691v1)

**Conditional optimization:** test automatic prefix caching only if prefill materially contributes and the exact tokenized preamble produces reusable cache hits. It skips shared-prefix computation, not decoding. Simultaneous first requests must not be assumed to reuse each other’s unfinished prefill. [vLLM v0.8.5 APC](https://docs.vllm.ai/en/v0.8.5/features/automatic_prefix_caching.html)

**Conditional calculation:** if prefill occupies fraction \(f\) of warm latency, even eliminating it entirely gives at most \(1/(1-f)\) speedup, holding queueing and other work fixed. Actual reuse removes only part of prefill.

**Smallest useful next experiment—proposed, not executed:** use ten fixed paper-extraction pairs near 4,000/200 tokens. Measure each individually, then as synchronized pairs, with prefix caching disabled; record one cold start separately. Inspect raw timings, medians, memory and preemptions rather than claiming stable tail percentiles. If the profile supports APC, replay those pairs with it enabled, separating empty-cache and primed-cache results and recording reused tokens. Retain it only for repeatable paired-completion improvement without worse evidence support or completeness.

GPU/runtime, prefix length/hits, cold-start frequency and Envoy’s quality benefit remain unknown.
