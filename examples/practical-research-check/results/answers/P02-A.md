**No—two simultaneous readers do not require twice the GPU memory. Recommend one shared serving engine with continuous batching**, loading Qwen3-8B and the adapter once. Two independent model-server processes normally duplicate weights, adapter storage, CUDA contexts and memory pools.

**Conditional calculation.** Qwen’s official configuration specifies 36 layers, 32 query heads, **8 KV heads**, head dimension 128 and no sliding window. FP16 and BF16 both use two bytes per element. Use the KV-head count, not the query-head count. [Qwen configuration](https://huggingface.co/Qwen/Qwen3-8B/blob/47719a242beab8f9aecc40ce3928b034dd5dd559/config.json)

For full attention, without prefix sharing:

`KV bytes = sequences × tokens × layers × 2(K,V) × KV heads × head dimension × bytes/element`

Thus each cached token requires **147,456 bytes (144 KiB)**. Reserving 6,000 input plus 256 output tokens per sequence gives:

| Memory component | One shared engine, two requests | Two independent servers, one request each |
|---|---:|---:|
| Base weights | W | 2W |
| Adapter storage | A | 2A |
| KV payload | 1,844,969,472 bytes = **1.718 GiB** | Same total payload |
| Allocator/workspace overhead | Engine overhead; depends on batch | Separate overhead for each server |

One sequence’s KV payload is **922,484,736 bytes = 0.859 GiB**. This assumes 6,000 includes the complete tokenized prompt and 256 includes all generated tokens. Cache-block rounding and metadata add memory.

Using Qwen’s rounded **8.2B** parameter count, unquantized 16-bit weights alone are approximately **16.4 GB / 15.27 GiB**. Shared weights plus two KV payloads therefore total roughly **16.99 GiB before adapter and overhead**; two independent unquantized copies exceed 24 GB before cache. Quantized weight residency remains unspecified; QLoRA training does not establish the inference loading format. [Qwen model documentation, April 2025 revision](https://huggingface.co/Qwen/Qwen3-8B/tree/47719a242beab8f9aecc40ce3928b034dd5dd559)

**Measured evidence and limits.** PagedAttention research demonstrated efficient KV allocation and batching on OPT/LLaMA models using A100 GPUs; it does not establish this Qwen deployment’s capacity. vLLM v0.9.2 documents cache preallocation, memory-consuming CUDA graphs and request preemption under cache pressure. Consequently, a preallocated engine’s reported VRAM may barely change between one and two requests. [Paper v1](https://arxiv.org/abs/2309.06180v1), [v0.9.2 implementation guidance](https://docs.vllm.ai/en/v0.9.2/configuration/optimization.html)

**Unknowns:** exact GPU usable capacity, weight format, adapter compatibility/storage, attention backend, prefill activations, graph/workspace allocations, fragmentation and latency. A 24 GB fit is plausible for a shared engine, but unproven. Envoy v5’s supported-answer improvement also remains unproven.

**Smallest useful next experiment—proposed, not executed:** pin those choices; warm one engine configured for two sequences and a 6,256-token maximum. Compare one request with one synchronized pair of distinct 6,000-token prompts, each forced to generate 256 tokens, disabling prefix reuse. Record device peak memory, allocated/reserved memory, KV capacity/occupancy, overlapping execution, preemptions and latency. Require both to finish without OOM or preemption and retain explicit memory headroom; otherwise queue the second request. One successful pair supports only this bounded admission envelope.
