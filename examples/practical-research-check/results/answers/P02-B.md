**Recommendation: use one shared serving engine with continuous batching. GPU memory need not double for two readers.** Keep two-request admission conditional on a memory measurement for the selected GPU, runtime and weight format.

**Measured evidence.** PagedAttention’s paper reports 2–4× throughput improvements over its baselines using OPT/LLaMA models on A100s with synthetic ShareGPT/Alpaca workloads. This supports the serving approach, but does not establish Qwen3-8B performance or 24-GB fit. Its §2.3 describes shared weights and iteration-level batching, where requests enter and leave between decoding iterations. [Paper, v1](https://arxiv.org/abs/2309.06180v1)

**Conditional calculation.** Qwen3-8B specifies 36 layers, 32 query heads, **8 KV heads**, and head dimension 128, with no sliding window. For FP16 or BF16 cache, each element occupies two bytes. Use the KV-head count, not the query-head count. [Official configuration, revision 47719a2](https://huggingface.co/Qwen/Qwen3-8B/blob/47719a242beab8f9aecc40ce3928b034dd5dd559/config.json)

\[
\text{KV bytes/token}=2_{\text{K,V}}\times36\times8\times128\times2
=147{,}456
\]

Assuming independent sequences, one completion each, no prefix sharing, and **6,000 total templated input tokens plus 256 generated tokens**:

| Memory component | One shared engine | Two independent servers |
|---|---:|---:|
| Resident weights | \(W\) | \(2W\) |
| KV per sequence | 922,484,736 bytes ≈ 0.859 GiB | Same |
| KV for both | 1,844,969,472 bytes ≈ **1.718 GiB** | Same aggregate |
| Other memory | Shared runtime plus concurrency-dependent overhead | Separate runtime overheads |

Using the model card’s rounded 8.2B parameters, FP16/BF16 weights alone are approximately 16.4 GB, or 15.27 GiB. Thus weights plus live KV are approximately **16.99 GiB shared versus 32.27 GiB independent**, before adapters and overhead. Two ordinary fully GPU-resident, unquantized servers therefore exceed 24 GB. Quantized weights change \(W\); they do not automatically change KV precision. [Official model card](https://huggingface.co/Qwen/Qwen3-8B)

**Overhead and unknowns.** Add adapter storage, CUDA context, prefill activations, attention workspaces, graph pools, allocator reservations and cache-block rounding. vLLM can size a KV pool from a configured memory budget, so device memory may remain nearly constant as cache occupancy increases. Its memory-utilization limit applies per instance; two defaults do not coordinate. Graphs also consume extra memory. Exact GPU capacity, quantization compatibility, Envoy adapter footprint and peak workspace remain unknown. [vLLM 0.10.2 arguments](https://docs.vllm.ai/en/v0.10.2/configuration/engine_args.html), [memory guidance](https://docs.vllm.ai/en/v0.10.2/configuration/conserving_memory.html)

**Smallest useful experiment—proposed only.** Pin the intended stack; set sequence limit 6,256 and concurrency two. Measure a warmed single-request baseline, then two distinct 6,000-token requests submitted together, forcing 256 generated tokens. Record peak device memory, allocator allocated/reserved memory, KV occupancy, overlapping execution and preemptions. Provision at least 12,512 token slots after block rounding. Admit two only if both finish without OOM or preemption and retain a predefined free-memory margin; otherwise queue the second request. This tests bounded admission, not supported-answer quality or Envoy’s benefit.
