This was a **development integration smoke**, not the paired Qwen3-8B base/v5 evaluation. It used the public Nebius `Qwen/Qwen3-30B-A3B-Instruct-2507` endpoint at temperature 0, 1,024 output tokens per turn, the Docker-only product investigator, and the frozen nine-note snapshot with corpus hash `a5470628a40fe6114271f3b2923ba025967bdc2552157543d2a7224440e43c47`. The hosted model's weight revision is not exposed by this API. The question references are agent-authored and have not received independent human review.

**Hypothesis:** a hosted Qwen can execute the Python search/read/passage protocol and supply a source-supported answer on a temporal question without inventing a result on an absent-outcome question. **Expected signal:** successful tool calls, sufficient quoted spans, and an explicit statement that a planned measurement has no recorded result. **Decision rule:** do not use this hosted worker for answer generation in the demo if either question lacks full support or invents a measured outcome. This smoke cannot decide whether v5 improves over base Qwen3-8B.

**Decision:** keep the hosted Qwen worker experimental and use the lexical evidence path for the demo. The first-search instruction solved the immediate no-tool-call failure, but it did not solve answer support or plan-versus-outcome reasoning. Do not tune on these two authored questions and then present them as held-out evidence.
