# Training Qwen as an executable personal-memory investigator

Research audit, September 28, 2026. This is a proposal and evidence review, not a new training result. It follows the executable-code task in [CODE_EXECUTION_SECOND_BRAIN.md](CODE_EXECUTION_SECOND_BRAIN.md): Qwen explores a frozen Obsidian snapshot with Python `search()`, `read()`, `passage()`, and `extract()` calls. A larger assistant may use its evidence in chat and the weekly research radar. A trained checkpoint succeeds only if it improves supported answers over the same base model on untouched code-execution questions without unacceptable execution, latency, or cost regressions.

## Conclusion

There is enough published evidence to justify **one bounded, verified-trajectory SFT experiment**, provided the personal-vault baseline exposes a teachable search/evidence failure. There is no published result showing that public multi-hop news/Wikipedia trajectories transfer to dated, heterogeneous Obsidian notes under our tool protocol, and no data-size guarantee for a $7 GPU balance. The next spend should not be GRPO, preference training, or continued pretraining. Those would add rollout/reward complexity before we know whether the task-aligned SFT signal works.

The most important local observation is the [September 28 matched memory screen](PERSONAL_MEMORY_READINESS_EVAL.md): base Qwen submitted 9/10 answers, with provisional blind AI-assisted grading of 5 pass / 4 partial / 1 fail; QASPER v5 submitted 3/10, graded 0 / 2 / 8, and had an execution-error episode on every question. V5 often guessed document IDs instead of discovering them with `search()`. These are agent-authored questions over nine synthetic notes, not independently reviewed real-vault performance. They nevertheless make further training from v5 a poor *default* bet. The September 26 [registered transfer protocol](TARGETED_QWEN_VAULT_TRANSFER_TEST.md) specifies continuing v5 to isolate added data. **Before collecting any training data or opening its held-out questions, amend that protocol prospectively if choosing fresh base Qwen as the primary initialization; keep v5 as a diagnostic comparator.** Do not silently present a changed initialization as the originally registered experiment.

Together these show that small models can learn **tool policies** from verified trajectories. They do not show that our checkpoint will improve personal-memory support. Local QASPER v5 is a direct warning that useful training loss or in-domain answers can coexist with worse cross-domain tool behavior.

## Public data worth converting

The datasets provide **questions, source documents, and offline labels**. None is already a valid `search() → observation → read() → observation → SUBMIT` training set. The student must see only the question and real tool observations; answer labels, gold document IDs, SQL, and source anchors stay in the offline verifier.

1. **[MuSiQue-Ans](https://arxiv.org/html/2108.00573), primary multi-hop source.** It has 19,938 official training questions with connected 2–4-hop support and more varied answers. This repository already has a 500-question training slice and an approximately 10,340-document corpus. The native 20-paragraph per-question setting is easier than searching a persistent vault, so measure the search difficulty after pooling a *train-only* document collection, and split by supporting documents/near-duplicate chains. Do not pool MuSiQue-Full's removed-support unanswerable cases and keep their original negative labels: the missing paragraph may reappear elsewhere in the pooled corpus. Recheck every negative against the full visible corpus or use isolated mini-vaults.
2. **[PerQA](https://huggingface.co/datasets/pchristm/PerQA), auxiliary personal/temporal source.** The current release separates personas across train/validation/test (12/2/6) and includes observable mail, calendar, social, purchase, workout, and media events with SQL-derived answers. Render *observable* events as dated Markdown notes and let Qwen search those notes. Keep canonicalized events and SQL invisible to the model and use them only to check outcomes. Its data is synthetic and structured-origin, not a substitute for authored Obsidian notes. Each persona may contain tens of thousands of events, so measure search/index capacity and use bounded, non-oracle subsets before conversion at scale. The [ReQAP paper](https://arxiv.org/html/2505.11900) is a precedent for executable personal-data plans, not for our exact adaptation.
3. **[MultiHop-RAG](https://arxiv.org/html/2401.15391), cheap conversion smoke and a minority of temporal/null examples.** It has 609 news articles and 2,556 questions, with 2–4 evidence articles for non-null cases. Its authors generate questions using the sources and include news-source information in question construction, so discovery can be easier than unnamed personal notes. More seriously, an audit of the [official JSON at revision `71ac0d0`](https://huggingface.co/datasets/yixuantt/MultiHopRAG/tree/71ac0d0) found that, after case-normalizing answers, `yes` (782), `no` (561), `insufficient information.` (301), `sam bankman-fried` (271), and `google` (211) account for **2,126/2,556 = 83.2%** of labels. Answer exact match can rise without improved document discovery. Pin raw JSON SHA-256 `03cfb4926461f868684903aadc8024447bdda5bb3f6804741424cce338515bff`. Use evidence coverage and a question-only control; do not make this the sole training or success set.

Keep [LongMemEval](https://github.com/xiaowu0162/LongMemEval) for an external memory diagnostic rather than training. Avoid using [PersonaBench's released GPT-4o data](https://github.com/SalesforceAIResearch/personabench) to train or select a competing Qwen model; its README explicitly restricts that use.

## How to turn labels into valid training examples

An accepted example is a **complete, replayed episode**, not `question → gold answer`. For an illustrative cross-note question, the assistant first calls `search("earlier view of X")`, receives actual note IDs, uses `passage()` or `scan()` to inspect a dated note, searches again using a term observed in the first result, inspects the later note, and submits a short claim with both source IDs and an explicit uncertainty if an outcome is absent. A recovery example can show a failed query followed by a justified rewrite. `read()` may return an entire long article, so bounded views should be preferred where they retain the required context.

Generate candidate rollouts with Qwen or a stronger teacher that sees **the same question, corpus, prompt, action budget, and tool results as the student**. Use gold support only after the rollout to accept/reject it. Reject hidden-answer queries, invented IDs, unexecuted observations, incorrect source claims, missing required evidence, false abstentions, and trajectories exceeding the product context/step budget. Replay accepted traces in the actual sandbox. Build a mix of bridge discovery, comparisons, temporal revision, no-answer cases, query repair, and evidence-based stopping. Group train/validation/test by source document or persona, not just random question row. For a held-out real vault, exclude its source notes and answer facts from public/synthetic training generation.

The existing [QLoRA trainer](../scripts/train_sft.py) already expands episodes into next-action targets, uses Qwen3's non-thinking inference prefix, masks preceding prompts and tool observations, and refuses sequences above 8,192 tokens. Reuse its pinned `Qwen/Qwen3-8B` revision, 4-bit NF4/BF16, rank-4 LoRA (alpha 8, dropout 0.05), microbatch 1, gradient accumulation 4, and seed 42 for one initial candidate. A one-epoch run with a predeclared learning rate (for example, `1e-4`) is a **cost-controlled hypothesis**, not a tuned optimum. Measure accepted trajectories, action tokens, sequence-length distribution, and a tiny optimizer timing sample before fixing the run. Keep a checkpoint/manifest with question IDs, source hashes, prompt/decoding, code/reward version, hardware, and cost. Preserve the existing MuSiQue reward as-is; its token-F1/citation formula does not judge semantic support for memory research.

**Why SFT first:** successful recorded behavior directly addresses v5's guessed IDs and broken search loop. The $7 balance cannot safely fund a Search-R1-style multi-rollout RL replication, and the current reward is misaligned with supported personal-memory answers. Preference optimization needs reliable, source-reviewed good/bad trajectory pairs; continued pretraining on notes would teach topic text, not necessarily tool decisions. Either can be considered only after the first matched SFT result identifies a specific remaining failure and a valid training signal.

## One decisive local test and budget stop

Use the existing [4-development/12-locked-transfer protocol](TARGETED_QWEN_VAULT_TRANSFER_TEST.md), after a *prospective* amendment for the chosen initialization and decision rule. A substantive read-only vault snapshot, human-checked source references, and paired base/v5 development outputs are prerequisites; the configured personal vault currently contains only `Welcome.md`. The nine-note synthetic screen is already consumed as development evidence and must not be reused as a held-out win.

**Hypothesis:** under the identical code-execution tools and prompt, action-masked SFT on verified open-corpus trajectories teaches Qwen to discover and inspect the required notes more reliably than pinned base Qwen, leading to more fully supported answers.

**Expected signal:** more questions with *every required note actually inspected*, more blind-reviewed fully supported answers, fewer guessed IDs/repeated or failing actions, and acceptable latency and cost. Also compare a fixed BM25 passage packet and, for the product, the same frozen host answering from each arm's evidence. Valid spans alone do not certify semantic support.

**Proposed go/no-go rule to register before the run:** on the 12 locked questions, require at least **three additional full supported passes versus base**, more than v5, no lower submission rate or higher execution-error rate than base, and no more than twice base's mean latency/cost on the same GPU class. This +3/12 is a pilot threshold chosen to demand a visible effect, not a statistical proof or forecast. If the baseline already has too little headroom, or a fixed retriever supplies the same evidence cheaper, do not spend the remaining balance on search-policy training. Passing still needs independent confirmation before a strong generalization claim.

The [historical optimization record](RETRIEVAL_TRAINING_REPLICATION_AUDIT.md) is 579 seconds for 35 conversations/106 actions on an A40, and 3 hours 20 minutes for 995 conversations/3,711 actions on a 32 GB RTX PRO 4500. These times exclude collection, download, evaluation, and idle pod time and cannot establish that a new run fits $7. Run CPU conversion/verification first; then cap a small GPU timing and baseline session, reserve enough balance for the locked comparison, and stop the pod when the artifacts are saved. Do not launch training until the real-vault entry gate and measured budget both pass.

## Unsloth and agent RL feasibility (September 28 follow-up)

**Decision:** Unsloth is an optimized training framework, not a different Qwen architecture. It is worth testing as an *isolated backend replacement* for the next justified SFT run. It does not change the current decision to establish the real-vault baseline and a support-aware training signal before RL. [Unsloth's RL guide](https://unsloth.ai/docs/get-started/reinforcement-learning-rl-guide) supports QLoRA/LoRA GRPO and vLLM; its Qwen3-8B L4 notebook is a single-answer reasoning recipe, not a drop-in trainer for our multi-turn Python-tool environment. Its hardware examples and memory claims are workload-specific; we have not measured fit or throughput at our 8,192-token cap.

The smallest controlled SFT trial changes only the loader/adapter implementation in an **isolated environment**, keeping the pinned `Qwen/Qwen3-8B` base revision, 4-bit NF4/BF16, rank 4/alpha 8/dropout 0.05, seed, data order, optimizer schedule, 8,192-token cap, and [`scripts/train_sft.py`](../scripts/train_sft.py)'s one-assistant-action-per-example `-100` labels. Verify identical token IDs and supervised-token positions on fixed examples before one forward/backward GPU step. Then record step time and peak VRAM against the current trainer, save a PEFT adapter, reload it through the real [`src/policies/qwen_common.py`](../src/policies/qwen_common.py) inference path, and replay a fixed tool episode with `enable_thinking=False`. The script's older built-in `sanity_check` prompt does not prove production prompt compatibility. **Hypothesis:** Unsloth lowers training memory or elapsed time without changing the learning target. **Signal:** matching masks and a reloadable adapter, plus measured lower resource use. **Decision rule:** abandon the swap if tokenization/loss masking differs, the adapter cannot run through the actual agent, or resources do not improve enough to justify a new dependency. This is a compatibility/timing experiment, not evidence of model improvement. Do not spend GPU credit on it before the real-vault baseline entry gate unless a no-cost GPU is available.

For later **multi-turn RL**, [Unsloth's agent guide](https://unsloth.ai/docs/get-started/reinforcement-learning-rl-guide/training-ai-agents-with-rl) points to [ART](https://art.openpipe.ai/fundamentals/training-loop/), which records complete trajectories containing the model's actions and real tool responses, assigns a terminal reward, and trains grouped attempts through Unsloth GRPO. An ART rollout would keep our exact `search/read/extract` and persistent Python execution, append each actual observation, and stop at `SUBMIT` or the existing step limit. [`LocalBackend`](https://art.openpipe.ai/fundamentals/art-backend/) can serve and train a LoRA on one GPU; the hosted backend has separate account and cost implications. ART can [warm-start from a standard PEFT SFT adapter](https://art.openpipe.ai/fundamentals/art-client/), but the regressed QASPER v5 should not become the default initialization. The repository's [`scripts/train_qasper_grpo.py`](../scripts/train_qasper_grpo.py) already performs multi-step Qwen3 rollouts; it remains a QASPER-specific comparison point, not a vault reward.

An RL reward must prefer **correct, supportable answers after necessary sources were inspected** and penalize fabricated IDs, unsupported claims, false abstention, and broken execution. Valid quotation spans alone cannot establish semantic support. Do not reward tool-call count or `search()` syntax as the main target. ART's example [RULER](https://unsloth.ai/docs/get-started/reinforcement-learning-rl-guide/training-ai-agents-with-rl) calls a paid judge (`openai/o3` in its sample), so it is not a free substitute for a reviewed verifier. Preserve the current non-thinking Qwen prompt and verify ART/vLLM renders the same generation prefix and trains only assistant actions, never tool observations. Pin ART/Unsloth/vLLM/Torch/CUDA in a separate environment: the older `requirements-pod.lock` is not a proven compatible RL stack.

**RL gate:** first freeze a substantive vault snapshot and named, human-reviewed baseline questions; define a deterministic outcome verifier that agrees with human support judgments on a small development sample; record group reward variance and baseline successful rollouts. Only then consider a capped one-batch ART fit/throughput check and a preregistered small training run, reserving credit for the untouched base-versus-trained comparison. Stop if rewards are nearly uniform, the verifier favors shortcut answers, the 8K-context rollout does not fit, or the $7 balance cannot cover training *and* evaluation. The model-improvement gate remains the paired held-out supported-answer result above; rising training reward is only a diagnostic.

The evidence now makes **multi-turn search RL a credible later experiment**, stronger than the generic math-GRPO notebook alone suggested. It also narrows the cheap-experiment claim: the closest exact-model search gains used tens of thousands of rollouts and multiple GPUs, while the closest exact-model Unsloth tool-format run reported no gain. Keep outcome-aligned SFT first at the current budget. If additional compute becomes available, compare an ART/Unsloth multi-turn RL arm against the same SFT and base controls with a reward tied to supported answers, not formatting or read counts; verify the Qwen3 thinking/non-thinking mode before changing it.
