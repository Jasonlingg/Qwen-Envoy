# Human learning, Nested Learning, and Envoy

**Recommendation (September 27, 2026):** Use multiple rates of *reviewing and revising evidence* as a product design hypothesis. Defer implementing Google's HoPE architecture or continually updating Qwen's weights for the October demo. A research assistant must first demonstrate useful, source-supported project continuity; a brain analogy cannot establish that benefit.

## What the papers support

| Finding | Evidence and boundary | Envoy implication |
| --- | --- | --- |
| Individual experiences can be learned quickly while more general structure develops across experiences. | [Complementary Learning Systems (McClelland et al., 1995)](https://web.stanford.edu/~jlmcc/papers/McCMcNaughtonOReilly95.pdf) is an influential computational theory. Its [2016 update](https://pubmed.ncbi.nlm.nih.gov/27315762/) discusses exceptions to a simple fast/slow split. It does not prescribe an AI note schema. | Preserve dated paper excerpts and experiment results as distinct evidence. Maintain an explicitly revisable project conclusion that cites them. Never silently overwrite an older conclusion. |
| Retrieving an idea can strengthen later retention more than simply restudying it. | [Roediger and Karpicke (2006)](https://doi.org/10.1111/j.1467-9280.2006.01693.x) and [Karpicke and Roediger (2008)](https://doi.org/10.1126/science.1152408) are controlled studies. Most evidence concerns student learning rather than ML research decisions. | At useful moments, invite the user to recall or predict before showing a paper summary or old decision. Make this optional and brief. A passive weekly digest is not retrieval practice. |
| Spreading practice over time helps later recall; the useful interval depends on the desired retention interval. | [Cepeda et al. (2006)](https://pubmed.ncbi.nlm.nih.gov/16719566/) synthesized hundreds of verbal-recall experiments. | Revisit an open project question after a delay, preferably when a new result or decision makes it relevant. Do not equate a fixed weekly notification with improved learning. |
| Feedback helps, but its information content matters. Correcting an error needs an explanation, not only a red mark. | A [meta-analysis of educational feedback](https://pubmed.ncbi.nlm.nih.gov/32038429/) found substantial heterogeneity. [Metcalfe's review](https://doi.org/10.1146/annurev-psych-010416-044022) covers learning from errors and corrective feedback. | When a run contradicts an expectation, show the earlier expectation, the observed result, the likely interpretation, and what remains uncertain. Ask the user to approve any revised conclusion. |
| Correcting a misconception is possible but not guaranteed to erase the old idea. | A [refutation-text meta-analysis](https://pubmed.ncbi.nlm.nih.gov/35095236/) finds benefits in learning settings. A [review of misinformation correction](https://www.nature.com/articles/s44159-021-00006-y) describes continuing influence after correction. These settings are not identical to research engineering. | Mark an older conclusion as superseded while keeping it visible and dated. Retrieval should prefer the current conclusion and still explain why it changed. |
| Recall can sometimes transfer to new problems, but transfer depends on the task and practice format. | A [meta-analysis of transfer](https://pubmed.ncbi.nlm.nih.gov/29733621/) found positive effects in some application and inference tasks and weaker effects in others. | Test whether the user can apply a learned research idea to a new experiment choice; do not judge learning by note count or repeated factual recall alone. |

Google's [Nested Learning paper](https://arxiv.org/abs/2512.24695) proposes nested optimization and a continuum of model memory update rates. Its HoPE results concern a model architecture, not a tested human learning intervention or proof that Envoy should train Qwen online. The resemblance to Complementary Learning Systems is useful inspiration, not a validated equivalence.

## Smallest useful workflow

For one active research project, accept the artifacts the engineer already creates: a rough notebook or Obsidian note, selected papers, code changes, and two run reports. Keep imported material read-only and dated. At a meaningful decision point, draft a compact card with **question, prior expectation, source claim, local test, observation, interpretation, unresolved issue, and next decision**. Require a person to confirm the interpretation. Later, answer “Why did we choose this?” using the original evidence and the dated decision. When new evidence conflicts, offer a revision with the old view still inspectable.

An optional learning interaction asks the engineer to predict the result of a new method or recall the reason for a prior decision before revealing the linked evidence. It should occur only when it helps the current task. The weekly radar can surface a paper against an open question, not send generic quizzes. Qwen can investigate relevant passages and run records with bounded read-only tools; Nemotron can discuss the implications. Neither model is allowed to convert a citation into a claim of semantic support on its own.

## What would change this recommendation

**Product hypothesis:** This workflow helps an engineer resume a project and choose a sound next experiment faster than their existing notebook plus search, without extra logging burden. Try it on one real project with a few papers, two run reports, and one changed decision. Have the engineer judge whether the assistant reconstructed *why* the decision was made, distinguished paper claims from local results, and offered a useful next action. If it only restates existing notes or adds chores, narrow or drop the feature.

**Separate model hypothesis:** On frozen, held-out code-execution project questions, trained Qwen must beat base Qwen on source-supported evidence work without unacceptable execution failures, latency, or cost. The human-learning papers do not establish that v5 meets this gate, nor do they justify another training job before the personal-vault baseline is reviewed.
