# Single-case experiment recovery pilot — protocol

## Question and fixed inputs

Can two Qwen v5 reader requests share one A5000, and do the recorded rounds
justify claiming a latency win? What is the cheapest useful next test?

The source is the already committed Qwen serving diagnostic and its existing
replayed experiment-mode record. The MCP store is regenerated by
`python scripts/demo_experiment_mode.py --output <new directory>`; that script
replays saved evidence without a model or GPU. No new diagnosis is written for
this pilot. The repository arm may read this repository's saved files. The MCP
arm may call only the local experiment-mode MCP's read tools against the
regenerated store. Neither may use web search, model inference tools, GPU,
training, or the other arm's answer. Fresh Codex CLI contexts use the same
model, prompt, read-only sandbox and maximum wall time of 180 seconds each.

## Predeclared check

Both arms must report: (1) the observations establish shared-engine admission
of two requests, not two loaded model copies; (2) the original speed difference
was not resolvable given the saved 0.4-second polling uncertainty; (3) the
latency claim remains inconclusive and the record is retrospective; (4) the
next test uses representative reader work and evidence/answer checks before
claiming speedup. They must cite local file or MCP record IDs and distinguish
observations from interpretation. An unsupported speedup claim is a severe
error. We will record tool failures, successful recovery, wall time, and CLI
token usage if emitted. A useful *single-case signal* requires the MCP arm to
be at least as accurate with no severe error and either at most 70% of baseline
wall time or at most 70% of baseline tokens. One case cannot establish a
general productivity advantage. Setup/import time is reported separately.
