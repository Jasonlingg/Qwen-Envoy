**Yes—speculative decoding merits a small, gated test, but the evidence does not justify expecting a 2× application speedup.** Two concurrent requests could leave capacity for parallel verification; whether they do depends on the unknown GPU, runtime and checkpoint. The 4,000-token inputs also make prefill overhead important relative to only 200 output tokens.

For this workload, my engineering assessment is:

- **Overhead and acceptance:** A separate draft adds prompt processing, serial drafting, synchronization and rejected work on the same GPU. Acceptance is unknown and depends on document tasks and sampling settings. High acceptance alone is insufficient: measured committed tokens per verification cycle must compensate for its entire cost.
- **Concurrency:** Two requests already share target weight reads through batching. Verification adds work to both, potentially reducing the spare capacity that makes speculation profitable. Benchmark concurrency two directly.
- **Memory:** An 8B target’s FP16/BF16 weights alone occupy approximately 16 GB, before caches and runtime allocations. At full output length, the two requests hold roughly 8,400 token positions. For ordinary transformer KV caches, storage is approximately `8400 × 2 × layers × KV_heads × head_dim × bytes_per_element`; those architectural details are unknown. Draft weights, draft KV, verification buffers and allocator reserve must also fit.
- **End-to-end benefit:** Speculation primarily accelerates decoding. If decoding were half the baseline latency, even doubling decoding speed would yield only 1.33× overall, before additional draft-prefill costs. That fraction must be measured.

Implementation support is version-sensitive. The **vLLM v0.10.2 documentation**, dated August 12, 2025, documents prompt n-gram proposals and model drafting, but warns that ordinary draft-model decoding is unsupported in v0.10.0 and that latency improvements are workload-dependent. It also documents numerical and batching qualifications to losslessness. This historical documentation is evidence of mechanisms and limitations, not confirmation of the unknown installed runtime’s support. [Documentation](https://docs.vllm.ai/en/v0.10.2/features/spec_decode.html)

**Smallest useful proposed test—nothing executed:**

1. **Gate first:** Record checkpoint/tokenizer revisions, GPU, runtime release, target/KV precision, sampling/logit processors and memory headroom. Require supported target verification and exact rejection sampling. Preserve the baseline target precision; quantizing it to accommodate a draft would change the comparison.
2. **Choose one candidate:** For extractive answers, start with verified prompt n-gram proposals, avoiding a second model’s weights and prefill. Otherwise use one compatible, substantially smaller draft only after confirming context/tokenizer compatibility and memory fit. Neither extractiveness nor a compatible draft is currently established.
3. **Compare:** Baseline is the same target/runtime with speculation disabled. Use three proposed tokens per cycle, 50 representative document pairs per arm, approximately 4,000 input/200 output tokens, concurrency two, warm-up excluded, alternating arm order and identical cache policy.
4. **Measure:** End-to-end p50/p95, time to first token, decode time, aggregate output tokens/s, peak VRAM, preemptions, proposal acceptance, committed tokens/cycle and drafting/verification time.
5. **Decide and stop:** Advance only with ≥10% lower median end-to-end latency, ≤5% worse p95/first-token latency, no throughput loss, and no memory or correctness failures. These are proposed engineering thresholds. Stop immediately on OOM, unsupported sampling or unexplained correctness differences; cap testing at one GPU-hour. Treat noisy results as inconclusive.

Exact rejection sampling preserves the target distribution within numerical limits; stochastic outputs need not match seed-for-seed. Require implementation convergence tests and a small greedy/reader-quality regression check; that check cannot prove distributional equivalence. Defer deployment if compatibility or guarantees remain unresolved.
